## 1. 产品视角

### 1.1 把三类用户砍成两类,押注交集人群

文档把目标用户切成"多人养宠家庭 / 老年慢性病 / 寄养出差"三类,但没说清谁是付费决策者、谁是日活使用者、谁是接收方。重新拆解:

- **P1 协同型主照护者(Sarah,32,双职工)**:JTBD 是"不想再为'你今天喂没喂药'吵架"。痛点是协作摩擦,不是记录本身。**关键判断:如果伴侣不加入,产品对她价值归零。**
- **P2 病历管理者(David,45,老年金毛)**:JTBD 是"3 分钟内把完整病史递给专科医生"。不需要多人协作,付费意愿最高、使用频次最低、最容易流失。
- **P3 临时交接者(寄养/出差)**:这是 Share 模块的子集,**不该作为独立人群招募**,它是 P1/P2 使用 Share 时的副产物。

**取舍建议:**
- 付费核心是 P2(痛点最痛、付费意愿最强、最容易用"先卖结果"验证)。
- 留存核心是 P1(日常任务产生日活)。
- 100 个创始会员应优先转化"**P2 痛点 + P1 行为**"的交集人群:有慢性病或老年宠物的多人家庭。VALIDATION.md 现在把招募配比平均切(8-10 / 3-5 / 3-5)是错的,应该 70% 押在交集人群。

### 1.2 用户旅程的三个生死节点

完整旅程:首次访问 → 信任建立 → 购买 → 提交资料 → 邀请第二人 → 日常使用 → 就诊触发 → 分享 → 推荐。三个致命节点:

**节点 1 — Landing 到购买的"信任悬崖"(情绪最低点)。** 用户看到的是还没做出来的产品,要他先付钱。当前 Landing 卖"创始席位 + 人工服务",但"承诺交付的边界"在 PRD 第 7 节是模糊的("核心产品访问权"未定义)。用户付钱时心理是"我在赌一个 promise"。

**节点 2 — 购买到第二次打开的"空窗期"(最高流失点)。** 付完钱、提交一次资料、收到一份人工 Summary,然后在 MVP 上线前没有任何理由第二天回来。这 7-14 天完全没设计留存机制。VALIDATION.md 的"第 3-7 天人工 Concierge"是访谈流程,不是付费用户留存流程。

**节点 3 — 第二位照顾者被邀请后"对方会不会用"(产品成立的真正验证)。** Sarah 邀请伴侣,伴侣要注册才能看任务。这一步的摩擦决定了产品是单人工具还是多人产品。Go 门槛写"至少 7 个家庭邀请第二位成员",但**没写"第二位成员是否真正完成过一次照护操作"**——邀请了不等于用了。

### 1.3 功能优先级:被高估与被低估的

**严重被高估:**
- **"今日照护"完整版(P0)**:这是一个完整的家庭任务管理系统,工程量被低估。真实使用前提是"已有两个活跃成员",但前 100 个用户里真正有第二位活跃成员的可能不到 30%。建议 P0 只做"今日清单 + 谁做了标记",跳过/重复/提醒下沉 P1。
- **Vet-ready Summary 的"自动生成"**:MVP P0 写"系统生成",但 AI 在 P1。**PRD 和 MVP 之间最大矛盾:营销大讲"professional pet AI",产品层面 AI 在 P1。** Phase 0/1 的 Summary 全部人工 + 模板化,Landing 不应暗示 AI 已在工作,否则是虚假宣传风险。

**严重被低估:**
- **"邀请第二位照顾者"流程**:它现在是 Today 的子项,但其实是 onboarding 核心。应是独立 P0 模块:邀请链接生成 → 对方免注册预览 → 注册引导 → 首次任务引导。转化率直接决定 Go/No-Go。
- **Share 的"接收方无需注册"**:这是 PLANET 唯一零摩擦触点和唯一病毒式增长来源。应提升为 P0 工程优先级最高。
- **"快速记录"输入摩擦**:PRD 原则写"拍照、语音、一句话",但 P0 语音在 P1、拍照没强调。记录不够快 → 时间线空 → Summary 没料。链路起点被低估。

### 1.4 三个致命产品风险

**风险 1 — 单人 vs 多人的根本矛盾(最高)。** 全部差异化押在"多人协作"上,但 100 个创始会员大概率是单人购买者。单人拿到多人工具,伴侣不配合,价值坍缩成"宠物备忘录"——替代品是 Notion 模板 / Apple Notes,免费且够用。VALIDATION.md 已写好退路(转单人 AI Vet Summary),说明创始人自己都不确定。**建议:Phase 0 强制要求每个付费用户 7 天内邀请第二人,邀请失败就当面访谈原因。**

**风险 2 — Vet-ready Summary 价值未验证就被当卖点。** 听起来对的痛点,但付费转化前提是"用户因这份 Summary 获得明显好处",这在 Phase 0 无法验证(还没真实就诊)。用户付的可能只是"我准备好了"的心理安慰。**必须在 Concierge 阶段跟踪:用户拿到 Summary 后真带去就诊了吗?兽医反应是什么?**

**风险 3 — 永久会员是商业定时炸弹。** 100 个永久会员 = 永久义务。产品做起来走向订阅后,这 100 人是"永远不付费的最活跃用户"。"核心产品访问权"边界模糊,必然产生纠纷。**必须在购买前明确列出永久会员包含什么、不包含什么,退款条件写成可执行条款。**

### 1.5 北极星指标

现有指标偏"使用行为",没有一个直接衡量产品价值是否成立。

**提议北极星:有效家庭数(Effective Households)** = 过去 14 天内,至少有 2 个成员在同一只宠物下各完成过 1 次照护操作的家庭数。同时绑定"多人"和"使用",任何一边塌陷就归零。

**还缺的关键指标:**
- 第二位成员激活率(被邀请后 7 天内完成首次操作的比例)
- Vet-ready Summary 使用率(生成后 30 天内是否真带去就诊/分享给兽医)
- Share 链接接收方打开率(病毒系数分子)
- 单宠协作密度(每只宠物平均活跃成员数,<1.5 说明退化为单人工具)

**警惕的虚荣指标:** Landing 访问量、邮箱收集数、社媒互动数、100 席售罄速度。这些不证明产品成立。

### 1.6 竞品与差异化

真正威胁不是 11pets/PetPal(功能型竞品,PLANET 有差异化),而是 **Notion 模板 / 共享备忘录**(行为替代品,免费且够用)。

差异化是否足够?判断是**不够**:
- "多人协作"依赖第二人配合,Notion 也能共享。
- "Vet-ready Summary"依赖 AI 质量,但 AI 在 P1,Phase 0 是人工的。
- 唯一结构性差异化是 **"Share 接收方免注册"** —— Notion 要登录、备忘录要账号、11pets 封闭。这是护城河,但现在只是 P0 子功能。

**建议:把"零摩擦分享"从功能升级为定位。** PLANET 不是"宠物照护协作工具",而是"**宠物世界的随时可交接入口**"——任何时候需要把宠物情况交给别人(兽医/保姆/家人/急诊),一个链接搞定。比现在的"协作 + 就医准备"更锋利。

### 1.7 Phase 0 → Phase 1 过渡决策

合并文档里两个互相矛盾的 Go 门槛(VALIDATION 第 3 节"订金 3 个" vs 第 5 节"全款 5 个"):

**硬门槛(全部满足才 Go):**
1. 收到 ≥ 10 笔真实永久会员全款
2. 其中 ≥ 5 个用户 14 天内邀请第二位成员
3. 其中 ≥ 3 个第二位成员完成至少 1 次照护操作
4. 至少生成并实际使用(就诊或分享给兽医)3 份 Vet-ready Summary

**软门槛(满足任一即预警):**
- 第二位成员激活率 < 40% → 多人故事存疑
- Summary 使用率 < 50% → 核心卖点存疑
- 创始会员 30 天主动打开率 < 30% → 黏性不足

**介于 Go/No-Go 之间:** 收款达标但激活不达标 → 先做 2 周"激活冲刺"(主动联系未邀请第二人的用户访谈阻力),冲刺后达标则 Go,否则转单人路线。

## 2. 技术视角

### 2.1 当前架构有一个真实的金钱 bug

Phase 0 的"Landing + Go webhook ledger"方向正确,但代码层面有**必须在进 MVP 前修复的硬伤**:

**【阻塞】名额超卖竞态(最严重)。** `db.go:96-117` 的 `insertPaidClaim` 在事务内 `SELECT count(*)` 再 `INSERT`,PostgreSQL 默认 READ COMMITTED 下两个并发 webhook 都会读到 99 < 100 然后都插入,结果是 101 条。LEMON-SQUEEZY.md:78 声称"跨实例并发安全"是**错误的**。修法:`SELECT ... FOR UPDATE` 锁计数器行,或 `pg_advisory_xact_lock`。100 个名额 + Lemon 重试,这个 bug 会在售罄边缘真实触发。

**其他生产稳定性短板:**
- HTTP server 无超时(`main.go:70` 裸 `ListenAndServe`),慢速攻击可耗尽 FD
- Lemon API 调用用 `http.DefaultClient` 无超时(`main.go:427`)
- 无优雅关闭,systemd 重启会中断正在处理的 webhook
- `/intake`、`/email-capture`、`/progress` 无速率限制,`pet_intake` 无唯一约束可被灌垃圾
- 无结构化日志(全 `fmt.Printf`)、无 DB migration 工具、无 Postgres 备份策略
- variant 档位硬编码在 Go 里,改价需重新编译部署

**修复成本约 2-3 天。**

### 2.2 MVP 技术架构方案

| 维度 | 建议 | 理由 |
|---|---|---|
| 前端 | 继续 Next.js,不转纯 React PWA | 现有 Next.js 15 + React 19 + Tailwind 4,迁移是纯损失;`/app/*` 加 manifest + service worker 即 PWA |
| 状态管理 | React Query + Context | MVP 规模不需要 Redux/Zustand |
| 后端 | Go 单体继续,不微服务,暂不接 saas-core | 7 endpoint → 约 20 endpoint 仍在单体能控范围;saas-core 留到真正需要会员计费时 |
| 认证 | Email magic link 为主(P0),Google/Apple OAuth 为辅(P1) | 契合"免注册低摩擦";用 SuperTokens 或 Clerk,不自建密码 |
| 实时协作 | SSE 优于 WebSocket | 任务同步是低频更新,SSE 单向推送 + POST 提交,比 WS 简单一个数量级 |
| 多媒体存储 | Cloudflare R2(无出口流量费) | 不要自建 |
| OCR(P1) | LLM vision(GPT-4o / Claude) | 一次调用同时完成 OCR + 结构化抽取,比先 Tesseract 再 LLM 更省 |
| AI 摘要 | Claude Haiku / GPT-4o-mini | 单次成本 US$0.001-0.003,延迟 3-8s 可接受;不自建 GPU |

### 2.3 关键技术难点

1. **多人勾选任务并发**:`task_completions` 用 `(task_id, date, user_id)` 联合唯一,先到者成功,后到者 409 + "already completed by Alex at 08:03"。前端乐观更新失败回滚。
2. **分享链接安全**:token 用 `crypto/rand` 32 字节 base64url(不用 UUID);过期服务端校验;撤销用 Redis 缓存;per-IP 速率限制防爬;建议 `share_id`(可枚举展示) + `secret`(鉴权)双段。
3. **重复任务 RRULE 调度**:看着简单实际是半个 Google Calendar(时区、夏令时、漏做补做)。用 `rrule.js` + 服务端预生成未来 30 天实例。
4. **多成员权限矩阵**:每行 timeline 查询都要 join care_members 校验 ACL,性能和正确性都要小心。

### 2.4 数据模型草案(核心实体)

```sql
users (id, email, display_name, created_at)  -- id 来自 auth provider

pets (
  id uuid PK, owner_user_id text, name, species, breed, birth_date,
  avatar_object_key, allergies text[], chronic_conditions jsonb,
  emergency_contact jsonb, current_medications jsonb, created_at, updated_at

care_members (          -- 多人照护 ACL
  pet_id, user_id, role owner|editor|viewer, invited_by, accepted_at,

  id, pet_id, title, rrule text,  -- iCal RRULE

task_completions (
  task_id, occurrence_date date, completed_by, completed_at,
  status done|skipped, note,
  PK(task_id, occurrence_date)  -- 防并发重复

timeline_events (
  id, pet_id, type symptom|weight|medication|vaccine|visit|photo|note,
  occurred_at, recorded_by, payload jsonb,  -- type-specific

  -- 索引 (pet_id, occurred_at desc)

share_links (
  id, pet_id, scope vet_summary|full_timeline|sitter_instructions,
  share_id text unique,  -- 可枚举展示

```

### 2.5 AI 能力的技术边界落地

"AI 做整理不做诊断"的技术落地:

1. **Prompt 硬约束输出格式**:System prompt 固定,输出 JSON schema,后端校验,不合规降级模板。
2. **来源可追溯**:每条 Summary 记录 `source_model`、`prompt_version`、`input_event_ids`,用户能看到"这个结论来自哪几条原始记录",一键导出原始数据。
3. **后置关键词过滤**:输出端跑"诊断/建议/疑似/确诊"检测,命中则灰显 + "以上为信息整理,不构成医疗建议"。

## 3. 商业视角

### 3.1 定价:阶梯聪明,但有两颗雷

阶梯设计本身聪明(10/40/50 切分,营收压在 #11-50 的 S$69.99)。但:

- **第一档跳价太猛**:S$23 → S$53 是 2.3 倍跳涨,刚看到第二条推文还没建立信任的用户大概率流失。建议改 #1-20 / #21-70 / #71-100,让中间档覆盖更多人。
- **永久会员是 SaaS 长期负债**:100 个 lifetime 用户永久占用 AI token + 存储 + 支持,按中度使用估算一年 US$600-1,800 纯成本,且随功能增加上升。"未来高成本服务可单独定价"的逃生口**必须在购买时写进 ToS 并显式同意**。
- **SGD 削弱转化**:目标市场是美/英/澳,美国用户看到 S$29.99 要 mental 换算。**建议页面上 USD 主显示、SGD 辅助**,或直接建 USD variant。

### 3.2 市场规模:可达市场比想象小,但足够验证

- 美国约 6,600 万养宠家庭,30-40% 多人共养 → ~2,000-2,600 万户
- 老年宠物(7 岁+)占 25-30%,慢性病长期用药 10-15%
- 两条件叠加(多人共养 AND 老年/慢性病),英语市场约 **300-500 万户**真实潜在用户
- 愿意为新 App 一次性付 US$23-97 的早期采用者,按 1-2% 渗透 → **3-10 万人**

**100 个创始名额作为验证规模偏激进。** VALIDATION.md 的 Go 门槛实际只需 5 个家庭付费。100 席是营销叙事,不是验证必要条件。风险是:7 天只卖出 8 个,"100 席"变成"卖不动"的反向社会证明。**建议软目标 20 / 硬上限 100,对外讲"前 20 席创始价",卖满再开放下一批。**

### 3.3 获客:7 天招满 100 人基本不现实

**纯 organic、7 天、100 付费用户、零粉丝新账号,统计上几乎不可能。** 各渠道现实预期:

- **X/Twitter**:零粉丝 thread 初始曝光几百,付费转化约 0。Building in public 需 4-8 周积累。
- **Reddit**:r/dogs 对"我做了个 App"高度警惕自我推广,大概率被删。合规发帖转化 0.5-2%,需上千曝光才有个位数点击。
- **Product Hunt**:三个里转化最好,但流量窗口 24 小时,需提前积累 hunter/maker 信誉,零背景冷发进 top 10 概率极低。
- **小红书/即刻**:S$29.99 ≈ ¥170 对小红书宠物用户属于"贵的新东西",转化低于英文市场。

**冷启动最大瓶颈不是渠道,是信任。** 卖一个尚不存在产品的永久会员,唯一信任锚点是创始人的狗和一段文字。按 1% 转化率,招满 100 人需 10,000 高质量目标流量,7 天纯 organic 到不了。

### 3.4 合规风险(最需立刻处理)

**卖不存在的产品的永久会员,在美/欧/新加坡都有消费者保护法风险:**
- 新加坡 CPFTA 禁止"不公平商业行为",预售需明确交付时间表和退款机制
- 美国 FTC 对 deceptive pre-sell 有执法先例
- 欧盟 14 天无理由退款权(数字内容除非明确放弃)

**FAQ 只说 "clear refund policy" 但没具体规则,这是法律敞口。** 必须在 checkout 前写明:交付时间表、退款条件、权益边界。Lemon Squeezy 作为 MoR 处理了 VAT/GST/PCI,但**不替你处理消费者保护法披露义务**。

**宠物健康数据合规:** PDPA/GDPR 下宠物数据本身不直接属个人数据,但与可识别自然人关联后受保护。建议数据最小化、明确隐私政策、提供导出和删除接口。

### 3.5 从 100 人到 SaaS

100 席售罄后切订阅,建议 **US$4.99-7.99/月 或 US$39-69/年**,家庭多成员共享一个订阅(不按人头),多宠物第一年免费、之后每只 +US$2/月。

**人工 Concierge 是规模化成本炸弹。** 每增加一个用户人工成本线性增长。必须在订阅上线前明确:**订阅只含自动化功能,人工服务是付费 add-on**(如 US$19/次病历深度整理)。

### 3.6 证伪信号

**该 pivot:**
- Landing 1,000+ 目标流量后付费转化 <0.3%
- 付费用户 <30% 提交真实宠物资料(买的是"支持你"不是"解决问题")
- 邀请第二位照顾者比例 <40%(多人假设证伪,转单人)

**该 double down:**
- 第一批 10 席 48 小时内售出
- 付费用户主动把 Summary 分享给兽医且兽医给正面反馈

### 3.7 文案:创始人故事不是最优钩子

"我给狗做了个 App"适合 building in public 长期积累,但不适合一次性冷启动付费转化——信任链太长(共情 → 理解问题 → 相信产品 → 掏钱)。

**更高效的钩子是问题前置 + 场景具象:** "上次兽医问你'症状什么时候开始的',你答不出来"——直接戳失败记忆,转化路径短一半。建议 A/B 创始人故事版 vs 场景痛点版。

**最致命的总体风险:** 不是定价也不是渠道,是**信任密度不足以支撑预售永久会员**。优先级应该是 48 小时内做一个可交互的 vet-ready summary demo(哪怕 mock 数据)放进 landing page,再开始导流。没有可触摸的产品瞬间,100 席的故事是空中楼阁。

## 4. UX 视角

### 4.1 三个场景的交互细节

**场景 A 多人照护:**
- 任务状态用「颜色 + 形状 + 文字」三重编码(色盲友好):待处理 = 空心灰圈,已完成 = 实心填充 + 勾选,跳过 = 虚线圈 + 横线
- "谁做了什么"用 16px 头像堆叠而非文字,当天最多 2 头像 + "+1"
- 已完成用温润 sage green(#7BA88F)而非亮绿;**避免用红色表示未完成(制造焦虑)**
- 低频成员(偶尔帮忙的室友)需「Guest View」:只显示"今天分配给你的 3 件事",不暴露完整 Pet 空间

**场景 B 就诊准备:**
- 遵循「3 tap to summary」原则:焦虑用户认知带宽极窄
- Today 顶部常驻 "Ready for the vet" 按钮,按时间窗口自动汇总,不让用户手动勾选
- **Summary 信息层级按兽医工作流排序**:① 基本信息 + 体重趋势 → ② 当前用药 → ③ 主诉与近期异常 → ④ 既往病史 → ⑤ 过敏与禁忌
- **过敏应单独提到顶部用色块标注**(会出命的问题),不要和既往病史混在一起
- **缺「本次就诊主诉 / Why now」字段**——兽医看摘要第一句想知道"今天为什么来",这是 DESIGN.md 的遗漏
- 缺「最近一次驱虫/疫苗状态」(兽医问诊高频项)

**场景 C 临时交接:**
- 接收方"不会下载、不会注册、不会登录、不会读说明",必须假设为零耐心
- 加载 < 1.5 秒,首屏看到宠物名 + 一句话价值说明,不要 hero 图占满屏
- 信任感建立:① 分享链接 preview(微信/iMessage)有 PLANET 品牌 + 宠物头像 + "Shared by [主人名]";② 落地页先展示真实内容,不立刻弹"输入邮箱";③ URL 用可读路径 `planet.pet/m/milo/r/x7k2` 而非一长串 token;④ 静态倒计时 "This link expires in 71 hours"
- 有效期默认值:7 天对两周出差不够,建议加 "Custom date"

### 4.2 界面交互质疑

- **Today 整点时间是幻觉**:DESIGN.md 示例 `08:00 早餐 / 09:00 用药` 误导。真实任务是"今天喂一次""随餐服用""隔 8 小时"。应区分**定时任务**(有钟点)和**今日任务**(无固定时间,chip 列表);药物支持"距上次 7 小时"相对提醒
- **Timeline 六类平铺是灾难**:默认按重要性而非纯时间排序(症状 > 用药变更 > 就诊 > 体重 > 照片 > 疫苗);三个一键 filter chip(Health / Care / All);同一天多个微小事件折叠成 "Aug 8 · 5 care logs"
- **Share 三类型是黑话**:Vet-ready / Full Timeline / Sitter Instructions 用户分不清。改为按接收对象命名:"For the vet → A clean summary of recent health"、"For a sitter → What to do each day"、"For everyone → Full timeline"

### 4.3 情感设计落地

- **配色**:奶油白底(#FAF7F2) + 暖灰文字(#3D3936,非纯黑) + sage green 强调。避免亮橙、婴儿粉、卡通黄
- **字体**:humanist sans(Inter / Source Sans),正文 16px,行高 1.5,段落间距宽松——"呼吸感"就是温暖
- **两种节奏**:医疗数据用紧凑间距 + mono 小标签(精确感);生活化内容用圆润卡片 + 稍大字号(人情味)
- **焦虑感管理**:健康异常事件用温和琥珀色边框(不用红色);提供 "Add a note to vet" 旁路,让用户感到"记录下来 = 已经在处理"
- **PET 彩蛋**:只在 onboarding 创建宠物空间时出现一次 wordmark 中 P-E-T 高亮,之后不再出现

### 4.4 可用性风险 Top 5

1. **邀请第二位照顾者失败**(协作冷启动)——被邀请人不知道自己要干嘛
2. **任务完成率低**(Today 空置变成焦虑源,最终卸载)
3. **Vet-ready Summary 生成后没人看**——兽医表示"我不看外部 App 链接"
4. **Timeline 记录衰减**——第一周热情,第二周停止。快速记录入口超过 2 步就失败
5. **多成员重复完成任务**——状态同步延迟导致重复喂药(健康场景真实风险)

### 4.5 用户研究建议

15-20 个访谈对**发现问题**够,但对**验证付费**不够。拆两阶段:
- 10 个深度访谈(60 分钟,回忆最近一次就诊/交接经历)
- 20 个短访谈(15 分钟,只问付费意愿与替代方案)

**访谈脚本别问"会不会用",要问"上次宠物生病,你怎么把信息告诉医生的?用了多长时间?有没有遗漏?"**——收集行为故事不是态度。

**免注册分享最低成本验证:** 不用做 PWA。写一封邮件/短信模板,内含真实可打开的静态网页(宠物信息 + 一段总结),发给 10 个真实养宠朋友的"虚拟兽医"。追踪打开率、停留时长、是否回复。如果静态链接打开率 <50%,PWA 版也不会好。

### 4.6 无障碍与包容性

- 老年用户(老年宠物主人本身是老年人):正文最小 16px,关键按钮 ≥48px,颜色对比度 AA 以上
- 非英语用户:避免俚语与动词短语("stay on top of"),Summary 字段名全球通用
- 视觉障碍:所有状态不仅靠颜色,VoiceOver 读屏顺序"任务名 → 状态 → 完成人 → 时间"

### 4.7 与 DESIGN.md 的分歧

1. Share 三类型术语命名 → 改按接收对象命名
2. Today 整点时间设计 → 误导性强,需区分定时 vs 今日
3. 首页三问与四 tab 的张力未解决
4. Vet-ready Summary 缺「主诉」字段
5. Logo 原则"避免地球/土星"过于保守——温和的轨道抽象符号是可识别资产,应 A/B 测试而非一刀切排除
6. "品牌语言轻量点缀"边界模糊:协作邀请应坚持 "Invite a caregiver" 功能语言,品牌语言只留在创建宠物空间这一刻

## 5. 四视角交叉发现:最高共识

四个独立视角不约而同指向了**同一个核心问题**:

> **"邀请第二位照顾者"是 PLANET 的生死线,但它在文档里只是一个子功能,在工程里被低估,在商业上决定了多人假设是否成立,在 UX 上是最大设计缺口。**

四视角的交叉建议:

| 视角 | 对"邀请第二人"的共识建议 |
|---|---|
| 产品 | 提升为独立 P0 模块,包含完整 onboarding 流程;Go 门槛加"第二人完成首次操作" |
| 技术 | 邀请链接 → 免注册预览 → 注册引导 → 首次任务引导,工程量被低估 |
| 商业 | 邀请比例 <40% 就该 pivot 到单人;邀请裂变是最强增长杠杆 |
| UX | 被邀请人的首屏体验完全没设计,这是最大设计缺口 |

**第二高共识:Vet-ready Summary 的"使用"比"生成"重要。** 产品视角强调要跟踪是否真带去就诊,商业视角把它当 double down 信号,UX 视角指出兽医可能"不看外部 App 链接",技术视角指出 AI 在 P1 而 P0 是人工的——营销和产品的矛盾必须解决。

**第三高共识:当前在卖一个尚不存在的产品,信任密度不足以支撑预售永久会员。** 商业视角最直白(需做 demo),产品视角指出承诺边界模糊,技术视角发现退款规则是法律敞口,UX 视角建议先用静态页验证接收方打开率。
