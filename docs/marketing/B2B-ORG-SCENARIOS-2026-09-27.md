# B 端组织场景评估：繁育场 / 猫咖 / 宠物医院 / 公益组织

日期：2026-09-27
触发：founder 问「这个 APP 有没有想过面向 B 端？它们会怎么用？有哪些场景？我们支持哪些？需不需要以及可不可以在后面做多租户？」
性质：战略评估（非实施计划）。结论先行，场景随后。

---

## 一、核心判断

**PLANET 的数据模型已经是「准组织」模型，B 端不需要另起炉灶。**

现有模型里「家庭」就是一个带角色的协作单元：owner / editor / viewer 四种角色、
宠物可跨家庭挂接（family_pet_links）、照护计划有值班指派、照护请求/转交在成员间
流转、宠物可移交给另一个家庭、对外有就诊快照分享页。把「家庭」读作「组织」，
猫咖和寄养网络今天就能用——这不是巧合，照护协同的本质在家庭和组织之间是同构的。

B 端缺的不是经典多租户（数据隔离已经有了：所有查询按成员关系收口），而是
**组织层（organization layer）**：组织级花名册、组织级角色与配额、模板化照护
方案、组织品牌的对外页面。这是一个增量层，不是一次架构重写。

**建议节奏：不做大跃进。** C 端留存尚未被证明（Phase 0 立场不变），B 端用
「现有产品 + 手工放行配额」先做 1-2 个友好组织试点，验证有人真用再建组织层。

## 二、四类组织的场景拆解

### 1. 公益组织 / 救助站（契合度 ★★★★★ —— 最佳楔子）

**它们的一天**：几十只待救助动物分散在寄养家庭里，组织要盯住每只的用药、
疫苗、复诊；寄养人交接（出差/退出）频繁；领养出去后要移交档案。

**用 PLANET 的方式**：
- 组织建一个「家庭」= 救助站，员工/核心志愿者是成员。
- 每只动物挂接到「救助站家庭」+「寄养人家庭」两边（family_pet_links 现有能力），
  组织保全局可见，寄养人执行日常照护。
- 班次/人力变动 = 照护请求与转交（现有能力）。
- 领养成交 = 宠物移交给领养人家庭（现有 transfer 流程），档案记录随行。

**缺口**：组织级跨家庭花名册（一屏看全部在管动物）、领养审核工作流、
批量导出、志愿者权限分层。

**为什么先打它**：使命契合（替你盯 = 防止动物在缝隙里被漏照顾）、迁移成本零、
transfer 流程就是为「动物换监护人」设计的；救助组织预算小但传播力强，
是口碑渠道不是收入渠道。

### 2. 猫咖（契合度 ★★★★ —— 最省心）

**它们的一天**：10-30 只常住猫，早晚班员工交接喂食/用药，某只猫状态异常要
全员可见，定期驱虫疫苗。

**用 PLANET 的方式**：店=家庭，员工=成员；排班交接=照护请求/转交；
异常记录=时间线。今天就能用，连 workaround 都不太需要。

**缺口**：班次表（谁几点上班）与照护指派对齐；顾客侧功能（店内猫咪名片/
点单联动）——那是另一个产品，不建议碰。

**价值**：单体付费意愿低但场景简单可视，适合做案例与传播素材
（「这家猫咖用 PLANET 管 20 只猫」）。

### 3. 繁育场（契合度 ★★★）

**它们的一天**：多窝幼崽，每窝疫苗/驱虫/断奶时间表错开，买家来接时要给
健康档案。

**用 PLANET 的方式**：场=家庭，每窝建组（缺口：窝/批次分组），
买家交付=transfer + 就诊快照页（现有分享能力直接当「电子健康护照」用）。

**缺口**：窝分组与批量操作（整窝同时接种）、宠物数量配额（几十上百只）、
买家只读视图。

**判断**：场景真实但预算小、数字化程度低，等组织层建好顺手支持即可，
不值得专门开路。

### 4. 宠物医院（契合度 ★★ —— 是渠道不是租户）

**关键认知**：医院已有 HIS/PIMS（病历、收银、预约），我们绝不去做院内管理。
PLANET 对医院的价值在**院外**：出院后的照护依从性。

**场景**：术后/慢病宠主回家执行用药与复诊计划（医嘱模板化成照护计划）、
主人到院时出示就诊快照（现有 take-to-vet 分享页就是为这个造的）、
医院以 viewer 边挂进主人家庭做随访。

**缺口**：医嘱模板库（术后 protocol 一键建计划）、医院侧的「我随访的病人」
列表、与 PIMS 的集成（深坑，别碰）。

**判断**：这是渠道合作（医院推荐主人下载 PLANET），不是把医院变成租户。
留作 B2B2C 分销通路思考，不进组织层首版。

## 三、我们今天已经支持什么（无需新代码）

| 能力 | 现状 |
|---|---|
| 组织=家庭，成员带角色 | ✅ owner/editor/viewer 四角色 |
| 一只宠物跨组织多方挂接 | ✅ family_pet_links（组织+寄养人） |
| 值班指派与班次交接 | ✅ 照护计划 assignments + 请求/转交 |
| 动物换监护人 | ✅ pet transfer 请求确认制 |
| 对外健康档案页 | ✅ 就诊快照公开分享（可当电子护照） |
| 按组织调配额 | ✅ plans 表运行时热调（人工放行即可试点） |

## 四、要不要、能不能后补多租户

**要不要**：要，但不是现在，也不是经典形态。C 端和 B 端共享同一套协同引擎
是 PLANET 的结构性优势——另建 B 端独立租户系统等于自断这条路。

**能不能**：能，且代价可控。当前所有数据已按 family_id 严格收口（应用层
成员校验），这就是应用层多租户。后补组织层的最小形态：

1. `families` 加 `kind`（household | organization）+ `org_name` 等少量列；
2. 组织角色映射进现有四角色（org admin≈owner、staff≈editor、read-only≈viewer），
   不发明第二套权限；
3. 组织级花名册 = 跨家庭宠物聚合只读视图（新查询，不动写路径）；
4. 配额/计费挂 plans 表（已是运行时数据）；
5. 对外分享页加组织品牌位（可选）。

隔离尺度升级（Schema 拆分/RLS/独立部署）留给真有合规要求的大客户那一天，
按现在的体量十年内用不上。

**现在就该保持的纪律**（零成本，防未来返工）：
- 新功能不要把「家庭=一家人」写死进语义和文案，统一当「协作单元」；
- 写路径一律过成员校验，不抄近道（现状良好，保持）；
- 配额继续只读 plans 表，不写死数字。

## 五、建议动作（按序）

1. **本周**：什么都不用建。如果 founder 想动，手工给一个友好组织
  （猫咖/救助站）开一个家庭 + 热调配额，让他们用现有产品跑两周。
2. **试点回收三个答案**：组织级花名册是不是第一痛点？角色够不够？
   宠物数量撞不撞配额？——这三个答案决定组织层建什么、不建什么。
3. **组织层立项门槛**：≥2 个组织真实在用且周活稳定，再动 schema。
