# PLANET 值班交班产品契约

状态：2026-09-09 · P1 已推进（服务端、Today、时间窗口、断网队列）

## 目标

让家庭成员用一句真实表达完成一段照护责任的转接：

> 我今晚加班，18:00—23:00 的照护交给你。

这不是把多条 Todo 转发给另一个人，而是把一个时间窗口里的照护责任交给下一位值班成员。所有具体照护仍以既有 Care Occurrence 为唯一事实主体。

## 用户体验

### 发起人

1. 在 Today 点击「交班」，而不是逐项点击「交给家人」；
2. 选择家庭、宠物范围、开始/结束时间；
3. PLANET 展示将被纳入的事项预览：宠物、事项、时间、风险级别、当前状态；
4. 选择接班人，补充一句话；
5. 发送一张交班行动卡；
6. 在对方明确接手前，发起人仍对未完成事项负责；
7. 对方只接部分事项时，发起人立即看到未接手清单，并可继续单项转交。

Today 首版提供三个明确范围：`今日照护`、`今晚 18:00—23:59` 与家庭时区下的自定义起止时间。服务端会校验每个 Occurrence 的 `due_at` 必须落在显式窗口内；起止时间会随离线命令一起保存，恢复联网后仍按原窗口发送。

### 接班人

行动卡必须让人不打开详情也能做决定：

```text
今晚照护交班 · 3 项
Milo · 18:00 遛狗
Milo · 19:30 喂药（重要）
Nori · 21:00 喂食

[我来做] [我也不行] [只做这些]
不方便？[给其他人]
```

「只做这些」先展示逐项选择，再提交明确清单。不能先把整批标成已接手，再让用户事后修正。

## 状态与事实

```text
Handoff Batch（聚合入口）
  ├─ Care Request → Occurrence A
  ├─ Care Request → Occurrence B
  └─ Care Request → Occurrence C
```

- `Handoff Batch` 只负责窗口、发起人、接班人、消息和展示聚合；
- 每个 `Care Request` 仍绑定一个 `Occurrence`；
- 每个 `Occurrence` 任意时刻最多一个有效负责人；
- 发送交班不等于接班，未回应前原负责人不失去责任；
- 批量接班必须在一笔事务中锁定并逐项校验；
- 某项已完成、已过期、已有开放请求或权限失效时，必须返回该项失败原因，不得返回整批成功；
- 事件审计按 Occurrence 记录，Batch 只提供关联 ID，避免以后无法解释某一项是谁接手的。

## 交互原则

1. **先看范围，再做承诺**：接班人必须看到事项清单和风险，不能只看到“3 项”；
2. **先承诺，再执行**：接手改变负责人；完成仍写入原 Occurrence 和 Pet Event；
3. **拒绝不能让责任蒸发**：「我也不行」返回继续转交，并显示未接手事项；
4. **部分成功必须诚实**：每项显示已接手、仍等待、已完成、已失效；
5. **通知是行动卡，不是聊天**：消息是上下文，按钮才是责任转移；
6. **接不了也要能接力**：接班人可以选择部分或全部未接事项，指定下一位家人；旧交班关闭为历史，新交班继续挂在同一批 Occurrence 上；
7. **完成是事实，不是承诺**：接班不等于完成，提醒和交班摘要都必须区分两者。

## 首版不做

- 不做跨天无限期值班；
- 不做自动替用户选择“只接哪些”；
- 不把整批拆成用户可见的多次重复提醒；
- 不在没有可执行 Occurrence 的情况下发送空交班卡；
- 不把值班交班做成聊天群或社交动态。

## 验收

- 3 项照护可以由一次交班表达发出；
- 接班人可以一次接全部，也可以明确只接其中几项；
- 接班前原负责人仍能看到未接手责任；
- 一项已完成不会被批量接班回写成 pending；
- 批量请求重复点击不产生重复 Care Request；
- 接班人可以将全部或部分未接手事项继续交给下一位家人，旧批次和新批次都保留在同一 Occurrence 责任链；
- 断网发送/接班会进入与单项照护相同的顺序队列，恢复联网后按原幂等键重放，且 UI 不伪装成已接手；
- Today、交班卡、收件箱、责任链和 Pet Event 对每一项显示同一事实。

## 已实现接口

- `POST /api/v1/families/{family_id}/care-handoff-batches`
- `GET /api/v1/care-handoff-batches/inbox`
- `GET /api/v1/care-handoff-batches/{id}`
- `POST /api/v1/care-handoff-batches/{id}/accept`
- `POST /api/v1/care-handoff-batches/{id}/decline`
- `POST /api/v1/care-handoff-batches/{id}/delegate`
- `POST /api/v1/care-handoff-batches/{id}/reassign`

客户端的 `batch-create`、`batch-accept`、`batch-decline`、`batch-delegate`、`batch-reassign` 与单项 `Care Request` 共用本地顺序队列。批量接班和继续转交的原子事实仍由服务端决定；本地队列只保存用户命令，不提前改写负责人。
