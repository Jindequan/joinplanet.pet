# PLANET 业务正确性重新验证

日期：2026-10-01（Asia/Singapore）。状态：**L154–L158 已在 1.1 工作分支修复并完成本批回归；全项目及 iOS 发布验收仍未完成。**

这是诊断、1.1 修复结果与整改验收清单，不是新的产品规范。业务裁决仍归 PRODUCT.md，动作规范仍归 APP-BEHAVIOR-CONTRACT.md。它记录当前代码与既有规范之间的差距，不新增产品方向、导航或数据结构。

## 1. 直接回答

项目有业务、对象、页面、权限、状态和数据变更文档，不能说完全没有设计。但“存在文档”与“设计在所有链路中成立”是两件事。此次验证发现：同一个照护事项，服务端检查的对象与实际更新的对象可以不同；前端允许的操作与后端允许的操作不同；内部与公开分享的状态词不同；完成后的查询刷新不完整；逾期规则与现行产品裁决不同。

因此，当前不能以页面数、接口数、测试绿灯或以前的审计评分承诺精确、优质的服务。也不能从这次有限验证推断每个流程都坏了。必须逐条建立业务规则→数据约束→事务动作→查询投影→用户反馈→验收证据的对应关系。

## 3. 已证实的断点（修复前取证，源码行号为当时定位）

### L154 / P1：补记日期绕过最终事项的责任守卫

业务规则：某事项已由 B 接受，A 不能代替 B 直接完成。直接请求确实返回 409 `CARE_OCCURRENCE_ASSIGNED`。

复现：同一计划的昨日事项作为 URL ID，body 传今日日期。代码先检查昨日事项的责任，然后物化并切换到今日事项，直接执行写入，没有对最终事项重跑责任守卫。

结果：返回 201；真实数据库中今日事项变成 `completed`，完成人为 A。检查对象与写入对象不一致，责任链约束被绕过。这是同一家庭内的业务权限绕过，不是已证明的跨家庭越权。

证据：`planet-api/internal/modules/tasks/service.go:2004` 检查；`:2082` 切换事项；`:2088` 写入；[backend-probes.log](business-review-2026-10-01/backend-probes.log)。

修复验收：最终 occurrence 必须先确定、锁定，再检查权限/责任/可执行状态并写入；日期不得成为逃逸路径。拒绝时 occurrence、事件、请求链均零变更。补记合法路径、并发接受/完成和同键重放必须同时成立。

### L155 / P1：B 已接手，A 的 Today 仍把它判为可执行并选为焦点

`today-rows.ts` 只拦 sent/seen 请求和待回应目标，未将 accepted-by-other 纳入 `canExecute`。模型探针得到 A `canExecute=true`，同一事项被选为焦点。卡片以 `canExecute` 决定执行控件，后端对 A 的直接完成返回 409（L154 的真实对照请求）。

证据：`APP/src/features/today/today-rows.ts:125`；`APP/src/features/today/cards.tsx:886`；[frontend-probes.log](business-review-2026-10-01/frontend-probes.log)。

修复验收：B 接手后 A 看见当前责任人和可用的查看/治理出口；B 可以执行；A 的焦点候选池不得包含这条不能执行的事项。送达中、等待回应、接受、撤回、完成、撤销都逐角色验证。

### L156 / P1：同日到点即显示逾期，违背现行裁决

`PRODUCT.md:152` 规定家庭时区次日零点才为 missed，当天未完成不算逾期。`task-time.ts:31` 却以 `due_at < Date.now()` 显示逾期；同页排序又以民事日期判断是否逾期。

复现：家庭时区 10 月 1 日 12:00，08:00 的 pending 事项。规范预期 false，当前函数返回 true。

证据：[frontend-probes.log](business-review-2026-10-01/frontend-probes.log)。

修复验收：按现行裁决收口判断；同日已到点、次日 missed、已完成、已跳过、跨时区、夏令时分别验证。时间提醒与逾期状态不得混成一套规则。

### L157 / P1：公开交接卡把已完成显示为未完成

真实路径：创建计划→完成→创建 care_card→匿名 GET 分享。接口返回 `tasks[].log_status="completed"`。公开页计数、勾选和样式三个位置均只识别 `"done"`。

结果：实际 1 项已完成，现有渲染表达式得到 0/1，且没有完成标记。该错误直接损害“交接时避免重复照护”的核心承诺。

证据：`planet-api/internal/modules/tasks/service.go:1770`；`www.joinplanet.pet/app/s/[token]/page.tsx:101`；[backend-probes.log](business-review-2026-10-01/backend-probes.log)。

修复验收：共享状态契约必须被真实 API 响应和真实页面消费共同验证；完成、跳过、未完成分别可辨认；撤销后新快照正确；旧快照仍按冻结语义展示。既有 L14（冻结快照却称 today/current）仍需兑现，不以页脚提示抵销主文案歧义。

### L158 / P2：完成/撤销后的查询失效遗漏协作和参与统计

完成后后端可能关闭请求并改变每周完成数。`invalidateAfterCareAction` 没有失效 inbox、sent 或 `family-participation`。参与卡没有轮询，且 `query.isError` 时直接返回 null。

结果：没有由这次写入保证的协作状态和统计同步；请求的其他轮询可能稍后修正，不能据此宣称即时一致。参与卡若持续挂载且无其他刷新触发，可继续显示旧数。读取失败又可能使该模块消失，而不是解释失败。

证据：`APP/src/core/foundation/cache.ts:60`；`APP/src/features/families/family-participation-card.tsx:32`；[frontend-probes.log](business-review-2026-10-01/frontend-probes.log)。

修复验收：以服务端写入副作用反推读面。完成/撤销后 Today、记录、请求、责任投影和周参与同步；刷新失败保留旧内容并说明陈旧/重试。成员变更也必须覆盖该统计读面。

## 4. 排除的疑点

曾怀疑“移动事项后显示新时间但排序用旧时间”。源函数在构造 `due_at` 与 `time_of_day` 不一致的输入时确会分歧，但真实 move 接口会同步更新二者。实测 08:00→18:00 后，`time_of_day=18:00`、`due_at=18:00+08:00`。**不将该疑点登记为已发生的缺陷。**

`isCareOpen(cancelled)=true` 暴露了模型对终态的兜底不足；尚未证明正常接口将这种行投影到 Today，因此也不作为已发生的用户问题登记。

## 5. 应采用的整改方式

### 5.1 先固定业务，再沿一条真实链路核对

当前核心承诺已有，不增加方向：多人照护时知道该做什么、谁负责、谁实际做了；历史可追溯；对外分享能正确交接。

第一条闭环：A 创建家庭/宠物/计划→邀请 B→双方看见同一事项→A 请求 B 接手→B 响应并完成→双方 Today/请求/记录一致→撤销恢复→分享并匿名读取→撤销分享失效。

对每一环标注现行规则、实际实现、验证结果和缺口。用此闭环审查对象与页面，不从已有按钮反推需求，也不靠增加功能抵销断点。

### 5.2 将六个设计面落实成可验证的同一套规则

| 设计面 | 必须回答并落档的内容 | 验收证据 |
|---|---|---|
| 业务定义 | 用户/角色、核心承诺、不做范围、成功与失败结果；每个规则有现行裁决 | 主闭环各环的 Given/When/Then |
| 数据设计 | User/Family/membership/Pet/ownership/link/Plan/Rule/Occurrence/Event/Request 的归属、基数、唯一性、状态终态、删除恢复与历史保留；事实与展示投影的区别 | 当前 36 次迁移叠加后的实际 schema 和数据不变量；事务前后 SQL 检查；不能仅评“3NF” |
| 后端逻辑 | 命令最终作用的对象、授权时刻、锁顺序、合法迁移、事务原子性、幂等绑定、事件和通知副作用 | 多角色真实 API；拒绝零写入；并发、乱序、超时重放测试 |
| 页面能力 | 每页唯一问题、主动作、数据来源、进入条件、角色边界、成功/失败/离开路径；sheet 与路由按任务选择 | 页面契约逐项与真实行为对照；页数本身不作为好坏标准，不擅改现有五 Tab |
| 交互与数据变更 | 每个按钮的前置条件、接口、字段变化、自动事件、缓存失效、用户结果、撤销 | 一份覆盖所有命令的动作矩阵；后端副作用与所有消费端一致 |
| 用户体验 | 加载/空/错/成功与业务阻断状态；权限不可用原因；失败保留输入；可恢复；时区/语言一致 | 390 与桌面真实截图和走查；首次最小动作计时；双账号切换；网络失败、旧缓存、深链与回退 |

### 5.3 动作矩阵的第一批实例

| 动作 | 权威数据变化 | 原子副作用 | 必须同步的读面 | 逆向/失败 |
|---|---|---|---|---|
| 完成/跳过一次照护 | 最终 occurrence 状态、实际执行人、执行时刻、备注 | 自动事实事件；关闭适用的请求链；绑定幂等资源 | Today、记录、请求、责任、统计、家庭参与 | 撤销；拒绝零写入；成功但回读失败保留重试身份 |
| 撤销照护 | occurrence 回待处理，执行字段按规则清理 | 原完成事实撤回；保留管理审计 | 同上，包含统计减少 | 7 天窗口、角色限制、重复请求、旧请求是否恢复按现行规则明确验证 |
| 请求/接受/拒绝/撤回 | 同一 occurrence 的责任链和当前责任人 | 请求事件；不另建待办；下游通知 | 双方 inbox/sent/chain、Today、责任投影 | 已处理/过期/成员移除时给明确出口；不可循环绕过拒绝 |
| 调整一次安排 | 指定槽位 override 与 occurrence 计划时间 | 适用的请求收束；不重写历史执行事实 | Today、计划预览、请求与后续分享来源 | 同键重放；skip/replace 终局保护；过期数据拒绝 |
| 生成/撤销分享 | 冻结 snapshot、token、期限、撤销字段 | 分享审计；匿名边界 | App 分享列表、匿名页 | 到期/撤销失效；显式快照日期；完成和跳过状态不失真 |

其余命令（账户、角色、成员、用药、计划版本、共享、转移、归档、离世、删除/恢复、照片）必须用同一格式继续核验，不能靠此次五项代表全量通过。

### 5.4 顺序与停线条件

1. 首先修 L154/L155：责任守卫和执行入口一致；补记变体不得改变权限。
2. 随后修 L156/L157/L158：状态判定、跨仓输出和读面同步。补覆盖这些业务规则的测试，不靠改断言迁就现状。
3. 再补齐所有命令的动作矩阵与数据不变量，优先核对停药/计划恢复、转移/共享、删除/恢复等逆向路径。
4. 用真实栈走上述薄切片，再逐页走角色、数据和错误状态。证据齐后才能恢复交付声明。
5. 已有业务规则内的修复直接执行；如确需改 IA/schema，先完成具体方案、迁移与回滚设计，再按项目约定裁决。不得用笼统确认阻断取证和方案设计。

通过标准：每个合法动作有预期数据结果；每个非法动作零副作用；所有消费页解释同一个事实；重试不重复、逆向可恢复；真实双账号闭环及异常场景有证据。尚未满足时明确写未完成，不再以“Almost Ready”代替业务验收。
