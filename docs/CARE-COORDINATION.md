# PLANET 照护协作系统

状态：2026-09-14

本文把 PLANET 的核心产品从“记录照护”推进为“让照护在家庭成员之间可靠流动”。

## 1. 产品判断

PLANET 不是普通的宠物待办，也不是家庭聊天工具。它是宠物家庭的照护控制中心：

> 每个人都知道宠物现在是否安全、下一件事是什么、谁正在负责，以及自己无法完成时应该把责任交给谁。

“接力”不是 Today 下方的一块附属 UI，而是每个需要协作的照护事项都可以进入的一层交互系统。

## 2. 核心交互语言

所有协作动作统一使用四个用户能立即理解的动作：

| 动作 | 含义 | 结果 |
|---|---|---|
| **我来做** | 接受这项照护责任 | 当前事项负责人变为我 |
| **我也不行** | 无法承诺完成，但不让事项消失 | 进入重新分配流程 |
| **给其他人** | 把责任继续交给指定成员 | 新成员收到行动卡 |
| **我做完了** | 事实完成 | Occurrence 完成并写入 Pet Event |

“我也不行”不能是死路；任何拒绝都必须继续提供转交、暂时无人接手或联系发起人的下一步。

## 3. 用户主流程

场景：Devin 今天加班，需要请伴侣晚上遛狗。

```text
Today 18:00 遛狗
  ↓
Devin 选择「给其他人」
  ↓
选择成员 + 可选备注 + 发送通知
  ↓
伴侣收到行动卡
  ├─ 我来做       → 已接手，所有相关成员看到负责人变化
  ├─ 我也不行     → 进入继续转交/无人接手流程
  └─ 给其他人     → 选择下一个成员并发送新请求
  ↓
接手人选择「我做完了」
  ↓
Occurrence 完成 → Pet Event → 家庭看到完成事实
```

通知不是单纯的提醒，而是可直接完成动作的行动卡：

```text
Devin 请求你照顾 Milo
今天 18:00 · 遛狗 · 约 30 分钟
“我今天要加班，晚上可能赶不回来。”

[我来做]  [我也不行]  [给其他人]
```

行动卡只发给当前 `target_user_id`。已经参与责任链、但不是当前接收人的成员收到不可操作的“转交反馈”，不会看到不属于自己的接手按钮。

行动卡中的 `due_at` 按 Family 的权威时区展示，而不是按查看者手机时区重新解释；这样出差、跨国或家庭成员设备时区不同，也不会把“今晚 20:00”显示成另一位成员的错误时间。`due_date` 只有日期时保持原日期，不被 UTC 转换跨日。

## 4. 状态模型

照护事项和协作请求必须分开：

- **Care Occurrence** 是唯一的照护事实主体，负责时间、规则、完成和历史。
- **Care Request** 是附着在 Occurrence 上的责任转接记录，负责请求、响应和通知。
- 不创建第二套 Todo、Relay Occurrence 或通知专用任务。

Care Request 状态（与 [APP-BEHAVIOR-CONTRACT.md](APP-BEHAVIOR-CONTRACT.md) §1 一致；2026-09-22 对齐，体检 P2-4）：

```text
sent → seen → accepted
            ├→ declined（拒绝后可由 reassign 在同一 Occurrence 上发起新请求）
            ├→ delegated（转交后新请求重新从 sent 开始）
            └→ expired（仅调度器写）
任意开放请求可 → cancelled；终态封闭。
```

`reassign` / `delegate` 是动作，不是状态。Occurrence 的 `pending / missed / completed / skipped / cancelled` 状态仍由照护地基管理，不能由 Care Request 复制或覆盖；撤销（undo）是动作与事件（care_task_undone），不是 Occurrence 状态。

### 4.1 规划中的扩展状态（未实现；2026-09-22 与契约对齐时移出）

以下状态链与 `undone` 用词来自早期规划稿，现行实现与行为契约均不存在，仅作历史设计参考，不得当作现行状态机引用：

```text
draft → sent → seen → accepted
                  ├→ declined → reassigning
                  ├→ delegated → sent
                  └→ expired → escalation
```

规划稿中 Occurrence 的 `undone` 同样未实现：现行契约里撤销是动作与事件，不是状态。

产品上必须始终能回答：

1. 这项照护现在是否有人负责？
2. 当前负责人是谁？
3. 请求发给谁、是否已查看、为什么没有接手？
4. 如果当前负责人失败，下一步是谁？

## 5. 界面规则

### Today 事项卡

每张未完成事项卡都要显示：

- 宠物和事项；
- 到期时间及逾期程度；
- 当前负责人或“还没人负责”；
- 请求状态（等待回应 / 已接手 / 无人接手）；
- 主动作“我做完了”；
- 次动作“给其他人”。

当请求仍处于 `sent/seen` 时，当前接收人必须先回应行动卡，不能直接完成；发起人仍可在等待期间直接完成或跳过作为兜底，系统会在同一事务中收束开放请求。开放请求未结束前，发起人不能再次创建第二张交班卡，避免同一项照护出现平行责任链。

待回应的协作行动卡在 Today 的视觉优先级高于值班背景、摘要和风险说明：用户先处理“有人正在等你回应”的责任，再查看统计或默认值班状态。风险和摘要可以补充上下文，但不能把当前行动压到普通待办之后。

当前 `完成 / 跳过` 只适用于本人直接执行或明确跳过；当事项属于另一位成员时，优先显示责任状态和接力动作。

Today 的每个协作事项还要在状态旁保留一条轻量责任链轨道：`发起人 → 当前接手人 → 下一位`。状态文案回答“现在发生了什么”，责任链回答“这项照护从谁流向谁”；当前用户在轨道中显示为“你”。这条轨道必须在主卡和列表行直接可读，不能要求用户打开详情才能判断交接关系。

### 请求卡

请求卡必须包含：宠物、具体事项、截止时间、发起人、接收人、上下文备注、当前状态和直接操作按钮。

Today 的责任投影还要保留下一环目标；在历史请求处于拒绝、转交或竞态收束状态时，不能只显示“已转交”，而要尽可能明确“下一位是谁”。

批量交班也必须逐项保留同一条责任链轨道；批量卡只能聚合数量和动作，不能把每个 Occurrence 压扁成一个不可解释的“已接手”。

请求卡可以出现在：

- 系统推送；
- App 内通知收件箱；
- Today 顶部的待响应区；
- 深链接打开的只读/响应页面。

不做无限聊天流。备注服务于照护上下文，结构化行动卡才是主体。

### 无人接手

请求在接近截止时间仍无人接受时，Today 必须显示明确风险：

```text
18:00 遛狗还没有人负责
[现在接手] [通知其他成员]
```

不能用“跳过”把这个状态隐藏掉。对药物、喂食等事项，风险级别和升级对象可以更严格。

## 6. 与现有地基的关系

现有 `pet_handoffs` 是“当前宠物由谁值班”的家庭级元数据，可以保留，但它不能承担所有协作交互。

产品上必须把两者明确区分：值班表示整只宠物的默认照看背景，不能等同于某一项
Care Occurrence 已被接手；具体遛狗、喂药、喂食等事项仍以 Care Request 行动卡和
Occurrence 执行事实为准。用户点击“我来值班”后，Today 不能因此隐藏具体事项的
“我来做 / 给其他人 / 我做完了”责任状态。

下一层应新增产品概念 `Care Request`，最小字段为：

```text
occurrence_id
from_user_id
target_user_id
state
message
created_at
seen_at
responded_at
response_note
supersedes_request_id
```

字段中的事项标题、宠物、到期时间和完成事实必须从 Occurrence 读取，不能复制成第二个事实源。

所有发送、接受、拒绝、转交、过期和取消都要产生可审计的协作事件；真正完成照护时仍只通过现有完成入口写入 Pet Event。

## 7. 施工顺序

### P0 API 契约

Care Request 只附着在现有 `care_occurrences` 上，客户端不创建第二套任务。当前后端接口固定为：

| 目的 | 方法 | 路径 |
|---|---|---|
| 发起请求 | POST | `/care-occurrences/{occurrence_id}/requests` |
| 查看待响应 | GET | `/care-requests/inbox` |
| 查看同一 Occurrence 的责任链 | GET | `/care-requests/{id}/chain` |
| 标记已读 | POST | `/care-requests/{id}/seen` |
| 我来做 | POST | `/care-requests/{id}/accept` |
| 我也不行 | POST | `/care-requests/{id}/decline` |
| 给其他人 | POST | `/care-requests/{id}/delegate` |
| 拒绝后继续转交 | POST | `/care-requests/{id}/reassign` |

所有写请求都要求 `Idempotency-Key`。`decline` 保留拒绝事实，`reassign` 创建同一照护事项上的下一张行动卡，保证“我也不行”不会成为流程终点。

整段交班沿用同一条责任链：批量接班人可以对全部或部分开放事项调用 `POST /care-handoff-batches/{id}/delegate`，也可以在批量拒绝后调用 `POST /care-handoff-batches/{id}/reassign`；旧批次保留 `delegated/declined` 历史，新批次继续绑定原 Occurrence，服务端在同一事务中保证不会留下两个开放请求。批量状态通知点击后，即使旧批次已离开收件箱，也必须展示原批次的只读逐项结果。

### P0 — 请求与响应闭环

1. 设计 Care Request 合同和状态转换；
2. Today 事项卡显示责任人与请求状态；
3. “给其他人”成员选择与消息输入；
4. 接收方行动卡：我来做 / 我也不行 / 给其他人；
5. 深链接和 App 内待响应列表；
6. 接手、转交、拒绝后的所有成员即时刷新；
7. 请求临近到期仍未接手时显示风险。

### P1 — 家庭照护规则

1. 默认负责人和备用负责人；
2. 临时请假和当天值班；
3. 批量交接晚间或整段照护（见 `docs/CARE-SHIFT-HANDOFF.md`）；
4. 自动升级到备用成员（首版已实现：仅对计划中明确配置的备用成员发起行动卡）；
5. 任务完成后向请求链相关成员回传结果。

### P2 — 外部照护者

1. 保姆、寄养家庭、亲友的限时协作；
2. 无需注册查看并响应单项照护请求；
3. 到期自动收回权限；
4. 受控的紧急联系人和交接摘要。

## 8. P0 验收标准

- A 能从 Today 把一项未完成事项发给 B；
- B 在 App 内或深链接页面看到完整行动卡；
- B 点击“我来做”后，A 和 B 都看到 B 成为负责人；
- B 点击“我也不行”后，不能停留在无后续动作的拒绝页；
- B 能把事项转给 C，C 收到新的请求；
- 任意时刻只有一个有效负责人；
- 同一请求重复点击不会生成重复转交；
- 负责人完成事项后，所有相关成员看到真实完成事实和执行人；
- 无人接手的事项在 Today 中明确显示风险；
- 断网、并发响应、过期请求、已完成事项再请求都不能造成责任状态与照护事实不一致。

## 9. 当前实现差距

截至 2026-09-08，Care Request P0 已有一条可运行的请求—响应—转交主链：

- 后端 `care_requests` / `care_request_events` 已落库，绑定单个 Care Occurrence；
- 已参与该 Occurrence 责任链的成员可以只读查看后续转交请求，便于打开状态通知追踪结果；只有当前目标成员拥有行动权限；
- 责任链只读权限仍受当前宠物/家庭访问权约束；成员退出家庭或失去宠物访问权后，旧通知不能继续读取照护请求，也不会再收到后续转交反馈；
- APP Today 可把未完成事项指定给某位家庭成员；
- 收件箱行动卡支持“我来做 / 我也不行 / 给其他人”；
- 点击协作通知后，Today 会直接显示这条照护的当前责任状态，即使用户当前停在其他宠物或其他范围；
- 通知动作成功、并发失效或请求过期后都带请求 ID回到 Today，由同一张协作结果卡呈现权威状态，不静默丢回首页；
- Occurrence 已转给其他成员后，Today 隐藏当前用户的“完成 / 跳过”动作，只显示负责人和等待状态，避免让非负责人误操作；
- 行动请求仍处于 `sent/seen` 时，目标成员必须先回应“我来做”或“我也不行”，不能绕过行动卡直接完成；请求发起人仍可在等待期间自行完成作为兜底；
- Care Request 一旦明确由 B 接手，完成接口也会阻止 A 通过旧页面或绕过客户端写入完成事实；没有发生临时转接时，原有计划协作者权限保持不变；
- Occurrence 完成或跳过时，事务内自动取消仍未响应的请求并写入取消事件；目标成员只收到一张不可操作的结束反馈，且反馈明确写出完成/跳过的执行人，不会同时收到重复的完成/请求通知；
- 接受会更新 Occurrence 负责人，拒绝后可继续生成同一事项的新请求；
- 临时接手只授权当前 Occurrence：接手者无需成为照护计划的长期协作者，也能完成这一次照护；不会悄悄改变后续排班；
- 所有关键写操作有幂等键，事件可审计，重复请求有唯一约束。

已完成的 P0 闭环新增：

- 临近到期的无人接手风险按小时持久化去重并自动升级；
- 请求链成员在真实完成后收到执行人和完成事实回传，幂等重放不重复通知；
- 照护请求、接手、拒绝和转交在断网时进入本地顺序队列，联网后按幂等键重放；
- 系统通知卡片也使用同一条照护动作队列：断网点击“我来做 / 我也不行”不会丢失，恢复联网后按原幂等键重放；
- 客户端显式配置前台通知展示；Android 使用独立的高优先级“照护协作”通知频道，避免请求已落库但系统通知被静默或落入不可见默认频道；
- 幂等重放不会重复发送照护推送；继续转交时，下一位接手人收到行动卡，已经参与这条责任链的成员收到转交反馈；
- 直接通知如果遇到推送/邮件提供商故障，会进入服务端 `notification_outbox`，由调度器按租约和退避策略补发；通知写入收件箱后不因外部通道短暂失败而丢失；
- 接受、拒绝和过期结果发给原参与者时只发送不可操作的状态反馈；只有当前 `target_user_id` 收到带“我来做 / 我也不行 / 给其他人”按钮的行动卡；
- 系统通知点击“我也不行”后与 App 内路径一致：拒绝成功直接打开“继续转交”，断网则在拒绝同步完成后打开；
- 通知动作断网进入本地队列后，Today 的结果卡立即显示“已保存，联网后自动回应/发送”，不把旧的“等待回应”伪装成最新结果；
- 通知设置页按家庭区分日常提醒、每日交班摘要和健康/照护预警；照护行动卡单独标记为始终开启，普通通知偏好不会让责任转接失去触达；
- Today 已接入家庭交班摘要卡：摘要项携带原 Occurrence ID 和最近 Care Request ID，点击后回到原日期并高亮照护事项；存在责任转接时继续显示同一条责任链，不生成摘要专用待办；
- Today 已接入照护风险卡：临近到期但无人负责、请求仍无人接手、接力已过期时，风险直接链接回原 Occurrence 和最近 Care Request；没有开放请求时，具备执行权限的成员可以直接“我来做”负责原 Occurrence，存在开放请求时必须先回应请求，不生成风险专用待办；
- 超过 `due_at` 仍未回应的请求由调度器原子收束为 `expired`，之后不能再接手。
- 计划中明确配置的备用成员在主负责人临近到期仍未完成时收到自动接力卡；只有确认接手后才改变 Occurrence 负责人。
- 备用成员顺序是照护计划上的显式优先级，可由管理员上移/下移；顺序变化只影响下一次升级，不改写已经发出的请求。

服务端前置验收可直接运行：

```bash
./scripts/acceptance-care-coordination.sh
```

该脚本会创建隔离的临时账号和家庭，验证请求幂等、接手、完成、拒绝、转交和转交后的完成闭环；它不替代下面的移动端通知、冷启动和断网验收。

仍需完成：系统通知动作在两套可操作移动端运行环境（iOS Simulator / Android Emulator，或另行授权的设备）上的展示、冷启动、断网重放、并发响应和过期请求端到端验收。本轮不得默认安装到实体手机；之后继续收束 P0，不扩展普通功能。
