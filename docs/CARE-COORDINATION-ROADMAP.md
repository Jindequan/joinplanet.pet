# PLANET 照护协作推进板

状态：2026-09-14

这份推进板只服务一个产品目标：**让家庭成员共同把一项真实照护完成，而不是各自维护一份待办。**

## 北极星

任意一项 Care Occurrence，在任何时刻都应该能回答四件事：

1. 现在谁负责；
2. 如果需要别人回应，下一步是谁；
3. 对方未能接手时，怎样继续转交而不制造第二份待办；
4. 最终是谁实际完成，并且所有相关成员看到同一事实。

因此，请求、通知、Today、收件箱、离线队列和 Pet Event 都只能围绕同一项 Occurrence 协作，不能产生平行任务源。

以上四问是过程追问；产品成败的量化判据（北极星指标 Weekly Active Pets 与安装→激活漏斗口径）见 [PRODUCT.md](PRODUCT.md) §3.2（2026-09-22 起归一入产品事实源）。

## P0：协作闭环

### 已完成

- 指定成员的照护请求：`我来做 / 我也不行 / 给其他人`；
- 接受后的一次性责任转接，临时接手者可以完成该 Occurrence；
- 拒绝保留历史，并进入继续转交；
- 请求、接受、拒绝、转交、过期、取消均有幂等键和事件审计；
- Today 显示等待回应、已确认负责、继续转交、过期和取消等责任状态；
- Today 将待回应的行动卡置于值班背景、摘要和风险说明之前，先让成员处理正在等待的家庭责任；
- 系统通知携带请求 ID，动作回到 Today 的同一行动卡；
- 单项请求和批量交班携带稳定的 iOS `thread-id`，不同待处理对象不会被系统合并成一张摘要卡；
- 接受、拒绝、转交支持断网保存，联网后按原命令顺序重放；单项或批量的离线拒绝在真正同步后都会恢复“继续转交/继续安排”路径，不会把拒绝变成无后续状态；
- 通知中心直接点击“我也不行”时，离线队列也会保留“同步后继续安排”的意图；只有服务端确认拒绝后才打开下一位选择器，不把未落库状态伪装成已拒绝；
- 完成与接手、完成与过期之间的竞态只有一个最终赢家；
- 事项先被完成时，开放请求自动取消并通知参与者真实执行人；
- 发起人在等待成员回应时仍可直接完成/跳过作为兜底；开放请求期间隐藏重复交班入口，避免同一 Occurrence 产生平行责任链；
- 发起人离线发送单项或整段交班后，Today 会把原 Occurrence 投影为“正在通知其他人”，在命令同步前关闭再次交班入口，避免离线期间重复创建责任链；
- 离线接受、拒绝或继续转交后，Today 会按原 Occurrence 投影“正在回应 / 继续转交”，在命令同步前关闭重复交班入口；继续转交命令未落库前，不允许把同一责任链再次发起；
- 离线队列遇到网络/401/5xx 错误时会停止重放并保留当前及后续命令；401 等待重新登录后使用原 commandId 重放，只有明确的业务 4xx 失效才继续处理下一条，防止后续转交越过尚未确认的拒绝或接手；
- 2026-09-10 已把队列重放提升到认证后的全局会话层：通知动作即使直接打开批量详情页，也会在冷启动、回到前台、队列写入后和短暂网络/5xx 故障恢复后自动重放；页面层与全局层按用户串行，不能并发发送同一个命令；
- 2026-09-10 已统一单项与批量面板的可重试判定：网络错误、未知网络异常和 5xx 都持久化原命令键，只有明确 4xx 才从队列移除并提示状态已失效；
- 2026-09-10 已把 Today 的完成/跳过离线事实提升到认证会话层：离开 Today、冷启动或回到前台后仍会自动重放；网络/401/5xx 保留当前及后续动作，明确 4xx 失效项移除并在手动重试时报告数量，避免离线事实永久挂单；
- 同一 Occurrence 后续发起的单项或批量交班自动继承最近一环，Today 发起的再次转交不会切断责任链；
- Today、收件箱和通知状态文案统一，旧转交记录不误指下一位成员。
- 2026-09-12 已补上 Web 同浏览器多标签即时同步：请求、接手/拒绝/转交、完成/撤销、临时记录及家庭/宠物治理写入后，其他标签页立即失效并刷新 Today、请求卡片、时间线和家庭工作区；不支持 `BroadcastChannel` 时降级到 `storage` 事件，跨设备继续由推送与轮询兜底。
- “我也不行”不会把责任链留在一张不可恢复的结果卡：没有下一位时明确显示“还没有下一位”，当前成员可以从状态卡再次进入“继续安排下一位”；只有真正创建下一环后才显示下一位成员。
- 单项转交选择器会读取该 Occurrence 所属照护计划的负责人顺序，明确标出“主负责人 / 备用 1 / 备用 2”；未配置成员仍保留在列表末尾作为人工兜底。
- 整段交班选择器会按选中项目计算成员覆盖度，优先展示能覆盖更多项目、且在相关照护计划中责任顺序更靠前的成员；仍允许人工选择未配置成员。
- 同一 Occurrence 的责任链不会循环回到已经明确拒绝或已超时的成员；单项与批量选择器会标明这些成员，服务端也会拒绝绕过 UI 的循环转交。
- 批量责任链按 Occurrence 逐项判断历史拒绝：成员只对其中部分项目不可再次接手时，选择器会自动排除这些项目并明确发送剩余数量，不把整批错误地吞掉。
- All / 家庭 / 宠物范围下的协作投影不再静默取第一个家庭：Today 会按当前可见家庭分别读取风险、值班、摘要和批量安排；同一只宠物属于多个家庭时，发起单项转交前必须明确选择家庭，并在卡片上标出家庭名。
- 2026-09-12 已把家庭与计划生命周期接回同一责任链：删除照护计划会取消未来开放事项并结束转交卡；家庭 owner 移出宠物时只取消该家庭的计划事项，不影响宠物在其他家庭的照护；家庭删除由 API 强制要求其他成员和宠物链接都已清空，不能只依赖页面禁用。

### P0 出口闸门

以下五项全部有设备证据后，P0 才算关闭：

1. 前台、后台、锁屏通知都能展示可操作行动卡；
2. 三个通知动作分别进入正确路径；
3. 冷启动和断网动作不会丢失、重复或伪装成功；
4. 并发响应、过期和重复点击不会产生两个负责人；
5. Today、收件箱、请求详情、Occurrence 执行事实和状态通知一致。

当前阻塞只在设备 UI 证据，不在服务端状态机：服务端 acceptance、客户端类型检查、Lint 和 iOS bundle export 已通过。

## P1：让“协作”成为日常习惯

P0 关闭后按以下顺序推进，每一项都继续复用 Occurrence：

### 1. 接力链可见 — 已推进

2026-09-09 已完成第一版：请求详情可以读取同一 Occurrence 的全部 Care Request 链，并在状态卡展示 `A → B → C`、每次状态、回应时间和回应备注；读取权限仍沿用参与者校验，不新增任务或 Occurrence。

实现：`GET /api/v1/care-requests/{id}/chain`，Today 通知回流后的协作状态卡；服务端 acceptance 已加入“拒绝 → 继续转交 → 接手”的责任链顺序断言。

在请求详情展示简洁的 `A → B → C` 责任链、每次回应和最终执行人。目标是让成员知道“谁曾经接过、现在轮到谁”，而不是只看到最后一张卡。

出口：同一 Occurrence 的链路可读、顺序稳定、不会把历史成员误显示为当前负责人。

### 2. 预设照护覆盖 — 已推进

备用成员现在有显式优先级，不再隐式依赖“谁先加入计划”；管理员可以在照护计划的负责人设置中上移/下移，页面按“主负责人 → 备用 1 → 备用 2”真实展示该顺序。调度器仍只创建一张 Care Request，按顺序逐位升级，只有明确接手才改写 Occurrence 负责人；自动升级也会继承最近一环的 `supersedes_request_id`，不会把责任链切断。

允许家庭为宠物和照护计划配置备用成员顺序；临近到期时只创建一张行动卡，第一位明确接手前不自动改写负责人。

出口：备用成员不会收到重复请求；任何自动升级都可追溯、可关闭、可按家庭时区工作。

### 3. 低打扰但不丢责任 — 已推进

2026-09-09 已把通知偏好落到设置页：普通的日常提醒、每日交班摘要、健康与照护预警可以按家庭分别开关；照护行动卡明确显示“始终开启”。

2026-09-09 已把 Family 时区带入 Care Request 与批量交班响应；行动卡和批量事项按家庭时区展示 `due_at`，避免成员设备时区不同造成误读，纯日期 `due_date` 不再经过 UTC 解析。

2026-09-09 已把照护通知 category、前台展示策略和 Android channel 的注册前移到 App 启动阶段；登录态只负责推送 token 绑定与动作执行，避免冷启动时因尚未完成登录而收到没有操作按钮的被动提醒。

2026-09-09 已在通知动作处理完成后消费并清除 Expo 的 last response；只有响应 ID 仍匹配时才清除，避免 App 重启重复执行旧动作，也避免处理期间的新点击被误删。

2026-09-09 已在 Today 打开“给其他人 / 继续安排”选择器后消费对应深链参数；用户取消后重新进入 Today 不会被旧通知参数再次弹窗，普通通知点击仍保留只读状态卡。

2026-09-11 已为普通家庭通知补上稳定的 Today 回流上下文：日常提醒、每日摘要和照护预警分别携带 `care_reminder`、`care_digest`、`care_alert`，点击后回到 Today 并刷新事实；它们不获得照护转接按钮，只有真正的 Care Request 才进入责任链动作卡。

2026-09-09 已把整段交班的风险上下文显式化：发起人与接收人都能看到“已逾期 / 已到时间 / 需尽快处理”标签，风险不再只由定点给药图标隐含表达。

2026-09-09 已统一 Today 与交班卡的逾期语义：Today 主卡和列表卡同时依据服务端 `missed` 或绝对 `due_at` 判断，不再用设备 UTC 日期猜测纯日期事项，避免跨时区家庭出现一边显示逾期、一边显示普通待办。

2026-09-09 已统一行动卡与推送正文的家庭时区：推送中的照护时间优先把绝对 `due_at` 转换到 Family timezone，只有历史数据缺少绝对时间时才回退到旧的 civil time；同一项照护在 Today、收件箱和锁屏通知中不再出现不同时间。

2026-09-09 已把家庭时区继续带入风险投影与责任链历史：风险卡的“快到时间”以及 `A → B → C` 的回应时间不再读取设备时区，而是使用同一家庭的时区事实。

2026-09-10 已修正跨家庭宠物从请求/记录回到详情页的范围继承：宠物范围携带的 `familyId` 会优先决定 Today、照护计划和时间线的家庭上下文；通知设置在多家庭未选定时不会显示可写开关。

2026-09-09 已统一批量状态卡的责任句式：不再只显示“成员 · 状态”，而是直接说明“等待谁回应 / 谁已确认负责 / 谁暂时不能做 / 下一位是谁”。

2026-09-09 已补齐批量交班推送的最小上下文：通知不再只有“共几项”，而会按家庭时区带出前两项宠物、照护标题和时间，并保留“还有几项”与发起人的留言；锁屏行动卡无需先打开 App 才能理解要接什么。

这里的边界是产品契约：偏好只控制普通通知的触达，不会静默“请你接手 / 我也不行 / 给其他人”这类责任转接行动卡，也不会改写 Care Request、Occurrence 或完成事实。后续再加入家庭时区、静默时段和“只发状态、不发动作”策略时，仍必须保留这条责任触达通道。

出口：用户可以降低打扰，但不会因为关掉普通提醒而漏掉一项已经交到自己名下的照护责任。

### 4. 交班摘要 — 已推进

2026-09-09 已在 Today 接入家庭交班摘要卡：按家庭聚合当天待处理、已完成、已跳过和预警；每条摘要项带回原 Occurrence ID，若存在最近一次转交则同时带回 Care Request ID。

点击宠物摘要会回到原日期和原照护事项，并高亮该 Occurrence；带有 Care Request 的摘要还会沿用 Today 的责任链状态卡，不创建新的 Todo 或摘要专用任务。

出口：家庭成员接班时能在一分钟内知道宠物今天的真实照护上下文，并能从摘要回到责任事实，而不是停留在一份孤立报表。

### 5. 风险回流到行动卡 — 已推进

2026-09-09 已把调度器发现的“临近到期但无人负责 / 请求仍无人接手 / 上一轮接力已过期”风险投影到 Today。风险卡保留原 Occurrence ID 和最近 Care Request ID，点击后回到同一项照护的执行卡与责任链；没有开放请求且用户有执行权限时，卡片还可以直接“我来做”，把当前 Occurrence 原子地归给自己。

这一步的产品原则是：风险提示必须带下一步行动，且不能为了提示风险而生成第二份待办。成员可以从原卡完成、跳过或继续给其他人；风险投影只负责把责任缺口显出来。

出口：无人接手风险在应用内可见、可定位、可处理；风险状态与调度器、Today 和 Care Request 使用同一事实源。开放请求必须先回应，不能用直接接手绕过责任链。

### 6. 整段照护交班 — 已推进

单项交接解决的是“这一次遛狗谁来做”，但真实家庭更常表达为“我今晚加班，晚饭、遛狗和喂药都交给你”。如果仍要求成员逐张发送行动卡，PLANET 会像待办转发器，而不是家庭照护的协作系统。

2026-09-09 已完成首版**批量安排**：Today 可以选择当前家庭的多项未完成 Occurrence，并限定为「今日照护」、 「今晚 18:00—23:59」或家庭时区下的自定义时间窗口；服务端校验每项 `due_at` 后，系统预览事项清单并发送一张行动卡。接收人看到事项数量、每项宠物/时间和风险提示，可以一次性选择「我来做」「我也不行」或「只做这些」；不方便时还可以选择未接事项并「给其他人」，把同一批照护继续安排给下一位成员。

实现约束：

- 交班卡只是协作入口，不是新的 Todo；每个 Occurrence 仍是唯一事实主体；
- 后端在一个事务内为选中的 Occurrence 建立同一 `handoff_batch_id` 下的 Care Request，全部成功或全部不发送；
- 接收人点击「我来做」后，逐项 Occurrence 原子确认负责；其中任何一项已完成、已过期或已有开放请求，都必须返回逐项结果，不能把整批伪装成成功；
- 「只做这些」必须让用户在回应前看到具体清单，未选中的事项仍由原负责人负责或继续单项转交；
- 「给其他人」必须在同一事务中关闭旧批次选中的开放请求、创建同一 Occurrence 上的新批次请求，并返回逐项结果；不能复制 Occurrence，也不能留下两个开放请求；
- 「我也不行」之后必须直接进入继续安排路径：对 declined 的选中事项调用批量 `reassign`，旧批次保留拒绝历史，新批次继续挂在同一 Occurrence 上；拒绝不能成为批量协作的终点；
- 交班窗口结束前，Today 显示“你仍负责未被接手的事项”，不能因为发出交班就让责任消失；
- 交班摘要和通知只聚合展示，点击后必须回到原 Occurrence 与责任链，不生成批量专用任务；批量状态通知即使对应批次已离开收件箱，也要展示原批次只读的逐项结果，不能丢失谁接手、谁拒绝、谁完成的上下文。

实现：`POST /api/v1/families/{family_id}/care-handoff-batches`、`GET /api/v1/care-handoff-batches/inbox`、批量 `accept/decline/delegate/reassign`；Today 已接入交班入口和聚合行动卡；批量创建、回应、继续转交与拒绝后重排已接入与单项协作相同的离线顺序队列；状态通知点击后回到原批次的只读结果卡。服务端 acceptance 已覆盖临近到期风险回流（含家庭时区）、3 项交班、部分接手、部分拒绝、幂等重放、继续转交、拒绝后重排以及与单项接力的并存。

出口：一个家庭可以用一次表达完成一段真实安排；所有事项仍只有一个负责人，部分成功有逐项事实，重复点击不会产生重复请求。批量断网队列已完成；离线点击「我也不行」会保留“同步后继续安排”的意图，拒绝真正落库后自动打开下一位选择器；原生通知批量动作仍列入下一轮设备验收，不把网络异常伪装成已确认负责。

## 明确不做

- 不做公开宠物社交、点赞、评论或聊天流来替代行动卡；
- 不把每次转交复制成新的待办；
- 不用 AI 猜测或自动宣称“已完成”；
- 不在 P0 设备闸门关闭前扩展商城、社区、复杂媒体或商业权益。

## 每次迭代的验收顺序

```text
产品状态机 → API 幂等/并发 → Today/收件箱投影 → 通知动作 → 断网重放 → 设备证据
```

任何一层失败，都先修复同一条责任链，再进入下一层；不通过截图推断服务端事实。
