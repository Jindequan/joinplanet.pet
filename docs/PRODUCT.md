# PLANET 产品事实源

状态：2026-09-14

本文是 PLANET 当前产品目标、业务对象、核心流程、范围和验收标准的唯一事实源。技术实现、表结构和 API 以 [ARCHITECTURE.md](ARCHITECTURE.md) 为准；**地基形态与延伸层接入**以 [FOUNDATION.md](FOUNDATION.md) 为准；原生 App 重建与视觉对照约定以 [APP/docs/PLANET_APP_DESIGN_SYSTEM.md](../APP/docs/PLANET_APP_DESIGN_SYSTEM.md) 为准（视觉冻结基准为 `mobile-v3/`）。

## 0. Slogan 与分层

**产品主张：** 把宠物照护安排好，家里人都知道下一步。

**产品语言规则：** 页面和通知只说具体的人、具体的事项和下一步动作；不使用“接住”“悬空”“彼此协作”“守护旅程”这类无法直接操作的抽象说法。家庭成员看到的动作名称固定为“我来做 / 我也不行 / 给其他人”。

| 词 | 产品含义 |
|----|----------|
| 我们 | 家庭共养是一等场景，不是单人工具 |
| 一起 | 可见、可请求、可接手、可转交、可交班（接力为延伸层） |
| 呵护 | 日常照护执行与关注 |
| 宝贝 | Pet 是被照护的个体，有档案与工作区 |
| 一生 | 事实流与档案跨生命周期累积 |

**四层（地基 → 延伸）：**

```text
L0 我们   Family / 成员 / 权限          ─┐
L1 呵护   计划 / Today / 用药            ├─ 地基（形态冻结，见 FOUNDATION.md）
L2 一生   Pet 档案 / Pet Event 时间线   ─┘
L3 一起   请求 / 接力 / 值班 / 交班摘要   ─┐
L4 对外   分享 / 趋势 / 导出 / 通知      ├─ 延伸（只接入地基 API，不改地基表）
                                         ─┘
```

**App 五 Tab 准入：**

| Tab | 必须回答 |
|-----|----------|
| 今天 | 此刻要为宝贝做什么？ |
| 请求 | 哪些照护请求需要我回应？ |
| 时间线 | 我们一起陪它经历了什么？ |
| 宠物 | 宝贝是谁、怎么照护？ |
| 更多 | 我们是谁、怎么在一起？ |

新功能必须标明层级与 Tab；延伸功能不得新建与 Occurrence/Event 平行的业务主体。

## 1. 产品定位

PLANET 是面向多人共养家庭的 Shared Pet Care System：把宠物长期照护计划变成今天可执行的行动，并留下可信的历史记录——**我们，一起，呵护宝贝的一生。**

核心承诺：**不用靠记忆管理宠物照护；今天该做什么、谁做了什么、宠物最近发生了什么，都能马上看懂。**

PLANET 不做公开宠物社交、点赞评论、AI 诊断、商城、保险或医生后台。

## 2. 真实用户与问题

- 两人或多人共同照顾宠物的家庭、伴侣和室友：避免漏做、重复做和责任不清。
- 老年、慢性病或长期用药宠物的照护者：持续执行计划并保留可追溯记录。
- 经常出差、寄养或临时交接的人：快速分享当前照护信息，不暴露不必要的隐私。

## 3. 领域对象与展示过滤

```text
User
├─ 多个 Family membership（owner / caregiver / viewer）
├─ Subscription / Entitlement / Usage
└─ Created Data

Pet
├─ Profile
├─ Medication
├─ Care Plan → Care Rule → Care Occurrence
├─ Pet Event
└─ 被多个 Family 共享

Family
├─ Members（owner / caregiver / viewer）
└─ Pet Visibility Links
```

- **Pet 是独立的核心领域对象和用户资产。** 它不属于某一个 Family；宠物档案、执行事实和事件跟着 Pet 走。长期照护计划属于一个 Family，因为规则的时区、负责人和协作成员必须有明确归属。
- **Family 是共享与治理关系。** 它定义哪些用户共同看到哪些 Pet，以及成员角色、邀请、家庭时区和提醒偏好；Family 不拥有 Pet。
- **一个 User 可以属于多个 Family，一个 Family 可以关联多个 Pet。** 同一只 Pet 也可以被多个 Family 共享；每个 Family 可以为这只 Pet 建立自己的照护计划和责任链，而完成事实与事件仍归到 Pet 的时间线，并保留发生时的家庭上下文。
- **成员角色决定可做什么。** `owner` 管理家庭、成员和家庭里的宠物；`caregiver` 可以参与照护、接收和转交请求；`viewer` 可以查看宠物与全部事件，但不能新增宠物、创建/修改计划、完成事项或成为照护负责人。
- **User Preference 是用户偏好。** `default_family_id` 和 `default_pet_id` 只决定打开 App 时的默认展示位置。
- **All / Family / Pet 是 UI 展示过滤条件。** 它们只影响查询参数和页面结果，不是 Context、Scope 或新的领域对象，也不改变权限关系。

### 3.1 照护闭环

```text
Family + Pet → Care Plan → Care Rule → Care Occurrence → Today
                                              ↓
                                  完成 / 跳过 / 撤销
                                              ↓
                                          Pet Event
```

Care Plan 是某个家庭针对某只宠物的长期照护意图；Care Rule 是循环规则；Care Occurrence 是一次真实执行。Reminder、Notification、Todo 都不是核心领域对象：提醒是 Occurrence 的下游通知，Todo 是 Today 的展示结果。

## 4. 核心体验

### 4.1 App 壳层

移动端使用原生 App 导航和底部主导航；桌面 Web 使用固定侧栏，两者共享同一组五个高频入口，不把协作请求藏在更多里：

1. **Today**：今天要做什么。
2. **Requests**：哪些照护请求需要我回应。
3. **Pets**：宠物工作区与切换。
4. **Timeline**：宠物最近发生了什么。
5. **More**：Family、Account、Settings、分享和其他低频管理。

顶部可出现 All / Family / Pet 过滤器，但它只是当前页面的查询条件。每一页必须明确当前 Pet、Family 或 All 的可见范围。

### 4.2 Today

- 首屏先回答“今天的照护状态”和“下一件最重要的事”。
- 事项按时间顺序展示，完成、跳过、撤销都能在原位置操作。
- 展示标题、宠物、时间、状态和执行人；说明信息按需展开。
- 日期按 Family 时区解释，存储和传输仍使用 UTC；支持有限的历史回看和补记。
- 网络失败保留草稿和页面结构，提供重试；不能静默丢失完成操作。

### 4.3 Pet 工作区

Pet 页面是围绕一只宠物的工作区，而不是资料杂项页：档案、用药、Care Plan、历史事件、趋势和分享在同一对象下组织，按任务优先级分层展示。

- 活跃 Pet 可读写，归档 Pet 可读但停止新照护执行。
- 删除是软删除和资产保护，不立即物理销毁历史；宠物所有者或关联 Family owner 可以发起，恢复仍由宠物所有者执行。
- 宠物转移必须保留历史，并明确旧 Family、目标 Family 和当前 owner 的变化。

### 4.4 Timeline

Timeline 是 Pet 的事实流，不是设置页。支持 note、symptom、weight、visit、vaccine、medication 和 care occurrence 等业务事件；未知事件类型必须能用通用卡片展示。

### 4.5 Family 与 Account

- Family：成员、角色、邀请、家庭时区、共享 Pet、提醒偏好、转移和删除恢复。
- Account：邮箱、显示名、语言、个人默认展示偏好、会话、注销。
- 只有 Family owner 能进行家庭治理和该家庭的 Care Plan 管理；普通 caregiver 可以执行被授权的照护事项。

### 4.6 受控分享

分享是 Pet 级的临时只读视图：`care_card` 提供当前照护信息和今日行动，不包含病史字段；`summary` 按选定范围生成健康摘要。分享链接必须有过期时间、可撤销；匿名接收方只能读分享快照，不能写入家庭数据。

### 4.7 页面质量基线

功能完成不等于页面完成。每个核心页面必须同时通过以下视觉闸门：

- **一眼知道重点**：首屏只有一个主叙事和一个主动作，不能让标题、说明、统计和按钮争夺同一层级。
- **动作有层级**：最重要的动作占据最清晰、最宽的触控区域；次要动作不与主动作挤成一排，也不能伪装成同等重要。
- **状态可读**：责任人、等待对象、下一步和完成事实不能藏在详情页；状态卡、责任链和结果反馈使用同一套语言。
- **密度有节奏**：卡片、页头、列表和底部导航共享间距、圆角、边界和颜色语义；多行内容不能继续使用单行胶囊样式。
- **表单能完成**：长表单、批量操作和键盘出现时，内容必须可滚动，底部主按钮始终能被看到和点击；不能因为弹层超出屏幕而截断流程。
- **移动端验收**：静态检查通过后必须在 iOS Simulator 或 Android Emulator（或另行授权设备）截图复核，至少覆盖空态、正常态、错误态、键盘态和长文案态。

当前已落地：登录页重做并修复输入框宽度；照护行动卡改为“主动作 + 次动作”层级；Today 页头、主照护卡和责任链状态卡收紧视觉密度；Today 已能在原 Occurrence 上调整本次时间或替代事项，不创建第二条待办。后续宠物页、时间线和更多页继续沿用同一基线，不再为单页临时添加另一套视觉语言。

## 5. V1 范围

### 必须完成

- 验证码登录、会话恢复、登出和账号设置。
- 创建/加入 Family、成员与邀请管理。
- 创建、编辑、归档、恢复、删除和转移 Pet。
- Care Plan 的 daily / weekly / monthly / interval 规则，以及临时照护使用的 once 规则；支持暂停/恢复、Occurrence 生成、Today 展示、完成、跳过、撤销和补记。暂停期间不生成新的 Today 待办，恢复后从当前家庭日期重新生成。
- Timeline 事件创建、分页、详情和删除权限；临时事件支持一张压缩照片和说明，照片随 Pet Event 保存，默认只对有权限的家庭成员可见，只有明确选入 `summary` 分享时才会出现在只读分享页。
- 用药开始、编辑、停止及其业务事件。
- `care_card` / `summary` 分享、匿名查看、撤销和过期。
- iOS、Android 和 Web 开发环境均能完成核心业务链路；移动端必须保持原生 App 结构，不引入 Next.js 页面模式。

### 明确不做

- 公开社区、点赞、评论、陌生人关注。
- AI 诊断或自动医疗建议。
- 通用媒体库、批量附件/文档、独立医生后台、商城、保险、硬件接入；当前只承诺临时事件的一张压缩照片，不把它扩展成平行媒体系统。
- V1 的付费订阅和复杂权益编排；计费数据结构预留，但不把未实现能力伪装成可用功能。

## 6. 关键业务流程

### 6.1 新用户到第一项照护

```text
登录 → 创建或加入 Family → 创建 Pet → 创建 Care Plan + Care Rule
→ 生成首个 Care Occurrence → Today 展示 → 成员完成 → 写入 Pet Event
```

### 6.2 多人协作

用户访问 Pet 的条件是：当前 owner、有效 Family 成员且存在有效 Family-Pet 共享关系，或有效的 Pet 级 delegation。Family 删除、成员退出、撤销 delegation 后，未来访问立即失效；已产生的 Pet 历史不被改写。

### 6.3 家庭和宠物生命周期

- 删除 Family：软删除 Family，结束成员关系并解除可见链接；Pet、Care Plan、Occurrence、Event 和 Medication 保留。
- 删除 Pet：宠物所有者或任一关联 Family owner 可软删除 Pet，停止后续照护生成；历史保留，恢复由宠物所有者在保护期内完成。
- 转移 Pet：以 pending → accepted / declined / cancelled 流程完成；接受后解除源 Family 的 live 可见关系，目标 Family 成为主 Family，宠物本体、时间线、照护事实和 Family-scoped 照护计划迁入目标 Family，旧分享失效。若旧 Family 还要继续查看，必须另行执行“共享”，不能把转移当共享。

### 4.4 Timeline 的离线事实

临时记录是用户已经发生的事实，不应因为瞬时断网而丢失。新增笔记、照片、体重、症状、就诊或疫苗记录在服务端暂时不可达时，会连同宠物、家庭上下文、发生时间和幂等键保存在当前账户的本机队列；登录会话在恢复联网、回到前台或定时重试时按原顺序同步。明确的权限或内容失效会从队列移除并提示，网络失败继续保留；同步前不在页面上伪装成已经写入服务端。

## 7. 验收标准

新用户应能在 3 分钟内完成：

```text
登录 → 创建/加入 Family → 创建 Pet → 创建照护事项
→ 看到 Today → 完成一项 → 在 Timeline 看到记录
```

双账号验收必须覆盖：A 创建 Family/Pet → 邀请 B → B 加入并看到同一 Pet → A/B 分别执行照护和记录事件 → 创建分享并匿名查看 → 撤销分享后失效 → Pet 转移、成员治理、Family 删除保护和恢复。

每个核心操作都必须有 loading、成功反馈、失败重试、权限失败和重复请求处理。断网、并发完成、过期链接、归档 Pet 写入、重复邀请码和配额不足不能导致用户资产丢失或状态半完成。

## 8. 迭代顺序

迭代必须 **先收束地基，再叠延伸**；细节与接口表见 [FOUNDATION.md](FOUNDATION.md)。

### Phase A — 地基收束（当前）

- 五 Tab 职责与 Scope 单一化；Today ↔ Requests ↔ Timeline 闭环稳定。
- 客户端 `APP/src/core/foundation/` 作为延伸层唯一写入口与 invalidate 图。
- 验收：3 分钟核心链路 + 双账号协作（见 §7）。

### Phase B — 延伸：接力（L3）**Care Request P0：代码闭环完成，Android Emulator 证据完成，iOS 系统 UI 证据待收尾**

具体的 P0 出口闸门与 P1 顺序见 [CARE-COORDINATION-ROADMAP.md](CARE-COORDINATION-ROADMAP.md)。

- 后端 `handoffs`：`pet_handoffs` 元数据 + 交班 note 写入 Pet Event
- `GET /families/{id}/handoff-summary` 聚合今日待办 + 当前值班
- APP Today 页「接力」条：接手 / 交班，不新建平行待办
- 已完成：Care Request 数据模型、指定成员、收件箱行动卡、接手、拒绝后继续转交、幂等与审计事件
- 已完成：推送携带请求 ID，点击回到 Today 收件箱；Today 显示等待回应、已确认负责、已转交和暂无负责人
- 已完成：临近到期/无人接手风险按小时持久化去重升级；按计划备用成员自动发起接力请求；完成后向请求链成员回传真实执行人
- 已完成：断网时按顺序保存请求、接手、拒绝和转交，联网后按幂等键重放；过期请求自动收束
- 已完成：系统通知卡片提供“我来做 / 我也不行 / 给其他人”；三项都进入同一条幂等离线队列，联网后自动重放
- 已完成：行动通知的推送/邮件失败会进入服务端持久队列，按租约、指数退避和最大尝试次数补发；提供商故障不会让已生成的照护请求失去触达机会
- 已完成：照护请求中心同时展示“有人请你帮忙”和“我发出的”；每条请求都能打开责任链或直接回到原来的照护事项
- 已完成：Today、请求详情、请求中心使用同一条家庭范围和 Occurrence 回流路径，不在请求页面复制待办
- 当前出口：两套可操作的 iOS Simulator / Android Emulator（或另行授权设备）验证通知展示、冷启动、断网重放、并发响应与请求过期状态；服务端验收、客户端静态检查和 iOS workspace 构建已通过。本轮原生验收只使用 Simulator，不安装实体手机。客户端现在会在“通知设置”明确显示本机推送登记状态（已登记、权限未开或登记失败），失败可重试，退出登录会删除本机令牌；不再静默把未登记设备当成可收通知。

### Phase C — 延伸：对外与监测（L4）**已完成 client 收口**

- `APP/src/core/extension/`：趋势、分享、导出、接力读写
- digest/alerts/notify 已有首版接入；当前预警包含体重变化、症状反复和已确认未完成的用药事项，并在 Today 摘要中提供回到宠物记录的操作入口。在 Care Request P0 设备出口关闭前，只修复责任链相关问题，不扩展普通功能。
